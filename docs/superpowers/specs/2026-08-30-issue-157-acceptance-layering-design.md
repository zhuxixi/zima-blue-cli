# Spec：github-issue-driven spec 阶段增加验收方式分层

**Issue**：#157
**日期**：2026-08-30
**状态**：设计已获口头确认，待用户审阅书面 spec

## 1. 背景与问题

`pi/github-issue-driven/SKILL.md` 的 Step 4 目前要求根据 issue 类型路由到 `systematic-debugging` 或 `brainstorming`，产出 spec / 根因报告，并在 spec 完成后暂停等待用户确认，但没有要求对每个功能点明确验收方式。

缺少这一步会造成两类遗漏：

1. 可以通过自动化验证证明的行为没有在设计阶段拆成可验证边界，实现时容易形成难以补测的耦合逻辑。
2. 需要真实使用才能判断的交互、外部系统或端到端效果没有形成实测清单，最终验收容易依赖临场记忆。

issue 原文使用“单测可验收 vs 用户实测”二分，但调研发现静态检查、集成测试、构建检查和自动化 E2E 也属于有效的非人工验收方式，不能统称为单元测试。因此本设计保留“两大类”结构，同时将第一类扩展为“自动化验证”。

## 2. 目标

修改 `pi/github-issue-driven/SKILL.md`，让验收方式分层贯穿：

```text
Step 4 spec 分类
    ↓ 验收编号
Step 6 plan 任务追溯
    ↓ 实际验证
Step 8–9 最终逐项对账
```

完成后，每个功能点都必须明确属于“自动化验证”或“用户实测”，并写明足以证明结果的具体方式和通过标准。

## 3. 设计决策

### 3.1 顶层分类：自动化验证 vs 用户实测

保留两个顶层类别：

- **自动化验证**：可以由稳定、可重复的工具或测试在本地/CI 完成验证，包括但不限于 `unit`、`integration`、`static`、`build`、`automated E2E`。
- **用户实测**：只有在真实使用环境中才能得到可靠反馈，或不适合用 mock/自动化环境替代的行为，例如真实交互体验、外部服务实际效果、真实部署后的行为。

“用户实测”不是自动化验证暂时没写出来时的兜底分类。若某项不能自动化，spec 必须说明原因，并提供操作步骤、观察结果、通过标准和可执行时机。

自动化验证优先选择**足以证明行为的最低成本层级**：能用 unit 验证的，不升级为 integration；必须跨组件时使用 integration；类型、格式或依赖约束使用 static/build；需要真实流程但可稳定脚本化时使用 automated E2E。

### 3.2 Step 4：spec 验收矩阵

Step 4 增加“验收方式分层（必答）”要求。每个功能点必须进入验收矩阵，至少包含以下字段：

| 字段 | 要求 |
|---|---|
| ID | 稳定编号，如 `A1`、`U1`，供 plan 和最终验收引用 |
| 功能点 | 本次改动具体要实现或修复的行为 |
| 验收方式 | `自动化验证` 或 `用户实测` |
| 具体验证 | 自动化类注明层级和命令；用户实测类注明操作步骤和观察结果 |
| 通过标准 | 明确何种结果算通过 |

建议在 skill 中加入可直接复制的示例：

```markdown
### 验收方式分层（必答）

对本次改动的每个功能点建立验收矩阵：

| ID | 功能点 | 验收方式 | 具体验证 | 通过标准 |
|----|--------|----------|----------|----------|
| A1 | 配置解析行为 | 自动化验证（unit） | `uv run pytest ...` | 相关测试通过 |
| A2 | CLI 跨组件行为 | 自动化验证（integration） | `uv run pytest ...` | 命令返回码和输出符合预期 |
| U1 | 真实外部服务交互 | 用户实测 | 按步骤执行并观察结果 | 外部服务产生预期效果 |
```

示例只用于说明字段和粒度，不要求每个 issue 都同时包含 A 类和 U 类条目。

### 3.3 Step 6：plan 追溯

Step 6 增加以下约束：

- plan 的每个实现 task 必须引用一个或多个 spec 验收 ID；
- 自动化验收项必须在对应 task 中落到具体测试、检查或构建命令；
- 用户实测项必须在对应 task 中落到实测步骤，或单独建立 post-implementation manual verification task；
- 不允许出现没有验收归属的实现 task；
- 不允许出现 spec 验收矩阵中没有对应 plan task 的验收项。

“引用验收 ID”是追溯要求，不规定 plan 必须采用某一种固定表格格式。

### 3.4 Step 8–9：最终验收逐项对账

本地 CR 与合并前检查必须按验收矩阵逐项核对：

- 自动化项记录实际执行的命令及结果；
- 用户实测项按清单实际执行并记录观察结果；
- 单测或其他自动化命令通过，不能替代尚未执行的用户实测；
- 用户实测暂时无法执行时，明确标记为 `pending`，不能宣称全部验收完成。

如果自动化验证失败，必须修复或明确阻塞原因；如果用户实测失败或 pending，合并报告必须如实呈现状态，不能用“测试通过”概括为全部验收通过。

## 4. 改动范围

### 修改

- `pi/github-issue-driven/SKILL.md`
  - Step 4：加入验收矩阵、两类验收方式、具体层级、通过标准和失败说明。
  - Step 6：加入 task 与验收 ID 的双向追溯。
  - Step 8–9：加入自动化结果和用户实测结果的逐项对账。

### 不修改

- 不新增独立 spec 模板。
- 不新增自动解析 spec 的契约测试。
- 不修改 `pi/issue-research/SKILL.md`。
- 不同步修改仓库外的 Claude Code skill。
- 不改变既有 worktree、subagent cwd、push gate、Zima CR 和 post-merge 清理规则。

## 5. 验收方式分层（本 issue）

本 issue 是 skill 文档改动，不改变 CLI、交互界面、外部服务或运行时行为，因此没有必须用户实测的验收项。

| ID | 功能点 | 验收方式 | 具体验证 | 通过标准 |
|---|---|---|---|---|
| A1 | Step 4 要求逐功能点建立验收矩阵，并区分自动化验证与用户实测 | 自动化验证（文本/结构检查） | 检查 SKILL.md 是否包含两类定义、矩阵字段、最低成本层级和用户实测失败说明 | 文案完整且没有把所有自动化方式错误称为单测 |
| A2 | Step 6 要求 plan task 与验收 ID 追溯 | 自动化验证（文本/结构检查） | 检查 SKILL.md 是否明确 task→验收项、验收项→task 的双向关系及两类 task 要求 | 追溯规则明确，无“只写测试即可”的歧义 |
| A3 | Step 8–9 要求最终验收逐项对账，不能用自动化结果替代 pending 用户实测 | 自动化验证（文本检查） | 检查 SKILL.md 是否包含命令/结果记录、实测记录、pending 和禁止替代规则 | 最终验收规则完整且与现有 CR/CI 门禁不矛盾 |
| A4 | 文案与当前单 Bot、worktree、push gate、清理流程兼容 | 自动化验证（全文审阅 + grep） | 审阅修改上下文并检查没有恢复双 Bot 或旧 worktree 规则 | 既有流程规则保持不变，无矛盾表述 |

## 6. 风险与降级

- **规则过重**：通过使用字段要求和示例，而不是强制独立模板或自动解析器，保持不同 issue 的 spec 结构灵活。
- **分类误用**：明确“用户实测”不是自动化验证缺失时的兜底，并要求写清无法自动化的原因。
- **追溯形式不统一**：只要求稳定 ID 和双向对应，不强制表格或文档格式。
- **用户实测不可执行**：允许标记 `pending`，但禁止把 pending 项包装成全部通过。

## 7. 成功标准

1. Step 4 明确要求每个功能点进入验收矩阵，并在自动化验证内部注明具体层级。
2. Step 6 明确要求 plan task 与验收 ID 双向追溯。
3. Step 8–9 明确要求自动化结果、用户实测结果和 pending 状态分别记录。
4. 文案不覆盖、不删除当前已经合并的单 Bot、worktree、cwd、push gate 和清理规则。
5. 修改范围仅限 `pi/github-issue-driven/SKILL.md`，不引入模板或代码测试。
